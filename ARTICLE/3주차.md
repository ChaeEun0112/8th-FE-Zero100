# [3주차]

## 1. 동적 라우팅, 중첩 라우팅, 쿼리 파라미터, URL 파라미터

### 1-1. 동적 라우팅 (Dynamic Routing)

동적 라우팅은 URL의 일부를 변수처럼 사용하여 하나의 컴포넌트로 여러 페이지를 보여주는 방식이다. 페이지의 구조는 같지만 게시글이나 상품처럼 데이터만 달라지는 경우에 유용하다.

```jsx
<Route path="/posts/:id" element={<PostDetail />} />
```

위와 같이 설정하면 `/posts/1`, `/posts/2`, `/posts/3`을 모두 `PostDetail` 컴포넌트로 처리할 수 있다. 게시글 상세 페이지, 상품 상세 페이지, 사용자 프로필 페이지 등에 활용할 수 있다.

### 1-2. URL 파라미터 (URL Parameter / Path Parameter)

URL 파라미터는 URL 경로 안에 포함되어 특정 데이터를 식별하는 값이다. 예를 들어 `/users/123`에서 `123`이 파라미터 값이다.

```jsx
<Route path="/product/:id" element={<ProductDetail />} />
```

컴포넌트에서는 React Router의 `useParams()`를 사용해 값을 가져올 수 있다.

```jsx
import { useParams } from 'react-router-dom';

function ProductDetail() {
  const { id } = useParams();
  return <p>상품 ID: {id}</p>;
}
```

`/product/1`에 접근하면 `id`는 문자열 `"1"`이 된다. URL 파라미터는 주로 특정 게시글이나 상품처럼 조회할 대상을 식별할 때 사용한다.

### 1-3. 쿼리 파라미터 (Query Parameter / Query String)

쿼리 파라미터는 URL의 `?` 뒤에 `키=값` 형태로 추가하는 정보다.

```text
/search?keyword=react&page=2&sort=latest
```

이 URL은 검색어가 `react`, 페이지가 `2`, 정렬 방식이 `latest`라는 조건을 나타낸다. 여러 값은 `&`로 구분하며 검색어, 필터, 정렬 방식, 페이지네이션 등에 활용한다.

React Router에서는 `useSearchParams()`로 쿼리 파라미터를 읽을 수 있다.

```jsx
import { useSearchParams } from 'react-router-dom';

function SearchPage() {
  const [searchParams] = useSearchParams();
  const keyword = searchParams.get('keyword');
  const page = searchParams.get('page');

  return (
    <p>
      {keyword} 검색 결과 - {page}페이지
    </p>
  );
}
```

### 1-4. URL 파라미터와 쿼리 파라미터 비교

| 구분      | URL 파라미터     | 쿼리 파라미터               |
| --------- | ---------------- | --------------------------- |
| 형태      | `/products/123`  | `/products?id=123`          |
| 위치      | URL 경로 내부    | `?` 뒤                      |
| 주요 목적 | 조회할 대상 식별 | 검색·필터·정렬 등 조건 전달 |
| 구분 기호 | `/`              | `?`, `&`                    |
| 예시      | `/products/123`  | `/products?category=shoes`  |

> **URL 파라미터**는 어떤 데이터를 보여줄지 식별하는 값이고, **쿼리 파라미터**는 데이터를 어떤 조건으로 보여줄지 지정하는 값으로 이해할 수 있다.

### 1-5. 중첩 라우팅 (Nested Routing)

중첩 라우팅은 부모 Route 안에 자식 Route를 구성하는 방식이다. 공통 레이아웃을 유지하면서 내부 콘텐츠만 바꾸고 싶을 때 유용하다.

```jsx
<Route path="/settings" element={<Settings />}>
  <Route path="profile" element={<Profile />} />
  <Route path="security" element={<Security />} />
</Route>
```

부모 컴포넌트에서는 `<Outlet />`을 사용해 자식 Route가 표시될 위치를 지정한다.

```jsx
import { Outlet } from 'react-router-dom';

function Settings() {
  return (
    <div>
      <Sidebar />
      <Outlet />
    </div>
  );
}
```

`/settings/profile`로 이동하면 `Settings`의 공통 레이아웃이 유지되고, `<Outlet />` 위치에 `Profile`이 렌더링된다. 설정 페이지, 마이페이지, 관리자 대시보드처럼 공통 레이아웃을 공유하는 화면에 활용할 수 있다.

### 1-6. 라우팅 방식 정리

```text
동적 라우팅
  /posts/:id
  └─ 경로의 일부를 변수처럼 사용

URL 파라미터
  /posts/123
  └─ 특정 게시글을 식별하는 값

쿼리 파라미터
  /search?keyword=react&page=2
  └─ 검색·필터·정렬 등의 조건 전달

중첩 라우팅
  /settings
  ├─ /settings/profile
  └─ /settings/security
  └─ 공통 레이아웃 안에서 자식 화면 변경
```

동적 라우팅은 경로에 변하는 부분을 정의하는 방식이고, URL 파라미터는 그 자리에 실제로 들어온 값이다. 쿼리 파라미터는 경로가 아닌 `?` 뒤에 추가 조건을 전달한다는 차이가 있다.

## 2. `useEffect`와 `useLayoutEffect`의 차이

React에서는 컴포넌트 렌더링과 관련된 부수 효과를 처리할 때 `useEffect`와 `useLayoutEffect`를 사용할 수 있다. 가장 중요한 차이는 브라우저가 화면을 그리는(Paint) 시점과 관련이 있다.

### 2-1. `useEffect`

`useEffect`는 외부 시스템과 동기화하거나, 데이터 요청 및 이벤트 등록처럼 렌더링 이후에 처리할 작업에 사용한다. 일반적으로 브라우저가 화면을 그린 뒤 실행되므로 대부분의 부수 효과에 우선적으로 사용한다.

```jsx
useEffect(() => {
  fetchData();
}, []);
```

화면에 먼저 표시된 내용과 Effect에서 처리한 결과가 다르면 상황에 따라 변경 전 화면이 잠깐 보일 수 있다.

### 2-2. `useLayoutEffect`

`useLayoutEffect`는 DOM이 업데이트된 뒤 브라우저가 화면을 그리기 전에 실행된다. DOM의 크기나 위치를 측정하고, 그 결과를 바탕으로 화면을 바로 조정해야 할 때 사용할 수 있다.

```jsx
useLayoutEffect(() => {
  // DOM의 크기나 위치 측정
}, []);
```

화면을 그리기 전에 작업을 수행하므로 변경 전 화면이 보이는 현상을 줄일 수 있지만, 작업이 끝날 때까지 Paint가 지연될 수 있다.

### 2-3. 차이 비교

| 구분      | `useEffect`                                  | `useLayoutEffect`                      |
| --------- | -------------------------------------------- | -------------------------------------- |
| 실행 시점 | 일반적으로 Paint 이후                        | Paint 이전                             |
| 주요 용도 | 데이터 요청, 이벤트 등록, 외부 시스템 동기화 | DOM 측정 및 즉각적인 화면 조정         |
| 화면 표시 | 대부분의 일반 작업에 적합                    | Paint 전에 반영해야 할 때 적합         |
| 주의점    | 경우에 따라 변경 전 화면이 잠깐 보일 수 있음 | 작업이 길면 화면 표시가 늦어질 수 있음 |

```text
useEffect
React 렌더링 → DOM 반영 → 브라우저 Paint → Effect 실행(일반적인 경우)

useLayoutEffect
React 렌더링 → DOM 반영 → Layout Effect 실행 → 브라우저 Paint
```

기본적으로는 `useEffect`를 사용하고, Paint 전에 DOM을 측정하거나 화면을 조정해야 하는 경우에만 `useLayoutEffect`를 고려하는 것이 좋다. 실행 시점은 렌더링 상황과 React 동작에 따라 세부적으로 달라질 수 있지만, 핵심적인 구분은 Paint 전후에 있다.

## 3. 브라우저 렌더링 과정

브라우저는 HTML과 CSS를 해석하고 화면에 표시할 내용을 계산한 뒤, 실제 픽셀로 그려 사용자에게 보여준다. 개념적으로 다음과 같은 단계로 이해할 수 있다.

```text
HTML 파싱 → DOM 생성
CSS 파싱  → CSSOM 생성
                ↓
          Render Tree 구성
                ↓
             Layout
                ↓
              Paint
                ↓
           Compositing
                ↓
             화면 출력
```

### 3-1. DOM 및 CSSOM 트리 생성

브라우저는 HTML을 파싱해 **DOM(Document Object Model)** 트리를 만든다. DOM은 HTML 문서의 요소와 계층 관계를 객체 구조로 표현한 것이다.

```html
<body>
  <div>
    <h1>Hello</h1>
    <p>World</p>
  </div>
</body>
```

CSS는 파싱되어 **CSSOM(CSS Object Model)** 구조를 만든다. DOM은 문서의 구조를, CSSOM은 스타일 규칙을 나타낸다.

### 3-2. 렌더 트리(Render Tree) 구성

브라우저는 DOM과 CSSOM을 바탕으로 화면에 표시할 요소와 스타일을 구성한다. 예를 들어 `display: none`인 요소는 화면에 표시되지 않으므로 일반적으로 렌더 트리에 포함되지 않는다.

### 3-3. Layout (Reflow)

Layout 단계에서는 요소의 위치와 크기를 계산한다. 너비와 높이, 요소 간 배치, 화면 안에서의 위치 등이 결정된다. 이 레이아웃 계산을 다시 수행하는 것을 보통 **Reflow**라고 부른다.

### 3-4. Paint (Repaint)

Paint 단계에서는 텍스트, 색상, 이미지, 테두리, 그림자 등 요소의 시각적인 부분을 그린다. 화면에 표시할 내용을 다시 그리는 작업을 **Repaint**라고 한다.

### 3-5. Compositing

브라우저는 필요한 경우 화면을 여러 레이어로 나누어 처리하고, 마지막에 각 레이어를 합성해 최종 화면을 만든다. 이 과정을 **Compositing**이라고 한다.

### 3-6. 렌더링 과정 정리

| 단계        | 역할                                       |
| ----------- | ------------------------------------------ |
| DOM / CSSOM | HTML 구조와 CSS 스타일 규칙 파싱           |
| Render Tree | 화면에 표시할 요소와 스타일 구성           |
| Layout      | 요소의 위치와 크기 계산                    |
| Paint       | 텍스트·색상·이미지 등의 시각적 요소 그리기 |
| Compositing | 필요한 레이어를 합성해 최종 화면 구성      |

실제 브라우저의 렌더링은 상황에 따라 일부 단계만 다시 수행되거나 최적화될 수 있다. 따라서 위 과정은 전체적인 흐름을 이해하기 위한 개념적 모델이다.

## 4. Reflow와 Repaint의 차이

웹 페이지의 DOM이나 스타일이 변경되면 브라우저는 변경 사항을 화면에 반영해야 한다. 이때 중요한 개념이 **Reflow**와 **Repaint**다.

### 4-1. Reflow

Reflow는 요소의 크기나 위치 등 레이아웃을 다시 계산하는 작업이다. 예를 들어 `width`, `height`가 바뀌거나 DOM에 요소가 추가되어 주변 요소의 배치가 영향을 받으면 레이아웃 재계산이 필요할 수 있다.

```css
.box {
  width: 100px;
}

/* 이후 width가 200px로 바뀌면 레이아웃 재계산이 필요할 수 있다. */
```

레이아웃 변경은 주변 요소에도 영향을 줄 수 있으므로 경우에 따라 처리 비용이 커질 수 있다.

### 4-2. Repaint

Repaint는 레이아웃은 그대로 두고 색상이나 배경처럼 시각적인 표현을 다시 그리는 작업이다.

```css
.box {
  background-color: blue;
}

/* 배경색만 바뀌는 경우에는 보통 레이아웃 재계산 없이 다시 그릴 수 있다. */
```

일반적으로 Repaint만 발생하는 변경은 Reflow까지 발생하는 변경보다 작업 범위가 작을 수 있다. 다만 실제 비용은 변경 내용과 브라우저 최적화에 따라 달라진다.

### 4-3. 차이 비교

| 구분      | Reflow                      | Repaint                                             |
| --------- | --------------------------- | --------------------------------------------------- |
| 의미      | 레이아웃 재계산             | 시각적 요소 다시 그리기                             |
| 주요 원인 | 크기·위치·문서 구조 변경 등 | 색상·배경 등 시각적 스타일 변경                     |
| 예시      | `width`, `height` 변경      | `background-color` 변경                             |
| 관계      | 이후 Paint가 필요할 수 있음 | 레이아웃이 변하지 않으면 Reflow 없이 발생할 수 있음 |

```text
레이아웃에 영향을 주는 변경
        ↓
     Reflow
        ↓
변경된 부분을 그리는 Paint 작업

레이아웃에 영향을 주지 않는 시각적 변경
        ↓
     Repaint
```

성능을 고려할 때는 불필요하게 DOM을 반복 변경하거나 레이아웃 정보를 읽고 쓰는 작업을 반복하지 않도록 주의해야 한다. 단, 어떤 CSS 속성이 실제로 어떤 렌더링 작업을 유발하는지는 브라우저와 상황에 따라 달라질 수 있다.

## 5. Context API 실습: 삭제 확인 모달 구현

### 5-1. 실습 목적

Todo List 프로젝트에 삭제 확인 모달을 추가하면서 Context API를 활용해 모달의 상태와 동작을 하위 컴포넌트에서 공유하도록 구현했다. 삭제 버튼을 누르는 즉시 항목을 삭제하지 않고, 확인 모달에서 사용자가 취소 또는 삭제를 선택하도록 구성했다.

이번 실습의 목표는 다음과 같다.

- Context API를 이용해 모달 상태 공유하기
- `useState`로 모달 열림 상태 관리하기
- Provider와 `useContext`의 역할 이해하기
- 모달 컴포넌트를 역할별로 분리하기
- 기존 Button 컴포넌트를 재사용하기

### 5-2. Context 생성하기

`ModalContext.jsx`에서 Context를 생성하고, 하위 컴포넌트가 Context 값을 사용할 수 있도록 커스텀 훅을 작성했다.

```jsx
import { createContext, useContext } from 'react';

export const ModalContext = createContext(null);

export const useModalContext = () => {
  const context = useContext(ModalContext);

  if (!context) {
    throw new Error('Modal 하위 컴포넌트는 Modal 내부에서 사용해야 합니다.');
  }

  return context;
};
```

`createContext()`는 Context 객체를 생성하고, `useContext()`는 가장 가까운 Provider가 전달한 값을 읽는다. 커스텀 훅으로 사용 방식을 한곳에 모으면 코드 중복을 줄일 수 있으며, Provider 바깥에서 잘못 사용했을 때 오류를 명확하게 확인할 수 있다.

### 5-3. 모달 상태 관리하기

`Modal.jsx`에서는 `useState`로 모달이 열려 있는지 관리했다.

```jsx
const [isOpen, setIsOpen] = useState(false);

const openModal = () => setIsOpen(true);
const closeModal = () => setIsOpen(false);
```

그리고 Provider의 `value`로 상태와 함수를 전달했다.

```jsx
<ModalContext.Provider value={{ isOpen, openModal, closeModal }}>{children}</ModalContext.Provider>
```

이렇게 하면 모달 하위 컴포넌트가 각각 별도의 상태를 관리하지 않고, 동일한 `isOpen`, `openModal`, `closeModal`을 공유할 수 있다.

### 5-4. 모달 컴포넌트 분리하기

모달을 하나의 파일에 모두 작성하지 않고 역할별 컴포넌트로 분리했다.

| 파일                | 역할                            |
| ------------------- | ------------------------------- |
| `Modal.jsx`         | 모달 상태 관리 및 Provider 제공 |
| `ModalContext.jsx`  | Context 생성 및 커스텀 훅 제공  |
| `ModalTrigger.jsx`  | 모달을 여는 요소 처리           |
| `ModalContent.jsx`  | 모달 콘텐츠 표시                |
| `ModalClose.jsx`    | 모달을 닫는 동작 처리           |
| `ModalBackdrop.jsx` | 모달 뒤의 배경 표시             |
| `Modal.css`         | 모달과 배경의 시각적 스타일     |

역할별로 분리하면 각 파일이 담당하는 기능을 쉽게 파악할 수 있고, 모달을 사용하는 코드도 읽기 쉬워진다.

### 5-5. Todo 삭제 기능에 적용하기

모달을 만든 뒤 Todo 항목의 삭제 버튼에 연결했다. 사용자가 삭제 버튼을 누르면 모달이 열리고, 취소 또는 삭제하기를 선택할 수 있도록 구성했다.

```jsx
<Modal>
  <Modal.Trigger>
    <Button variant="danger">삭제</Button>
  </Modal.Trigger>

  <Modal.Backdrop />

  <Modal.Content>
    <h2>할 일을 삭제할까요?</h2>
    <p>삭제한 할 일은 복구할 수 없습니다.</p>

    {/* 취소 및 삭제하기 버튼 */}
  </Modal.Content>
</Modal>
```

동작 흐름은 다음과 같다.

1. 사용자가 삭제 버튼을 클릭한다.
2. `openModal()`이 실행되고 `isOpen`이 `true`가 된다.
3. 모달 콘텐츠와 배경이 표시된다.
4. 취소를 누르면 모달을 닫고 Todo를 유지한다.
5. 삭제하기를 누르면 해당 Todo를 삭제한 뒤 모달을 닫는다.

기존 `Button` 컴포넌트를 재사용해 프로젝트 내 버튼 스타일을 일관되게 유지했다. 이번 실습을 통해 Context API가 여러 컴포넌트 사이에서 공통 상태와 함수를 전달할 때 유용하다는 점을 확인했다.

## 6. Tailwind CSS, ESLint, Prettier, React Router 설치 및 설정

### 6-1. Tailwind CSS

Tailwind CSS는 미리 정의된 유틸리티 클래스를 조합해 스타일을 적용하는 CSS 프레임워크다.

```jsx
<button className="rounded-md px-4 py-2">추가</button>
```

이번 Todo List 프로젝트에서는 기존의 컴포넌트별 CSS 파일을 활용해 UI를 구현했기 때문에 Tailwind CSS를 실제 스타일링에 적극적으로 사용하지는 않았다. 대신 설치와 개발 환경 설정을 진행하고, 기존 컴포넌트 구조와 스타일을 유지하는 데 집중했다.

### 6-2. ESLint

ESLint는 JavaScript 코드에서 잠재적인 오류나 프로젝트의 코드 규칙 위반을 검사하는 도구다. 프로젝트에 설정된 스크립트가 있다면 다음 명령어로 실행할 수 있다.

```bash
npm run lint
```

ESLint는 사용하지 않는 변수나 import, 문법 및 코드 규칙 위반 등을 확인하는 데 도움이 된다. 다만 실제 검사 항목은 프로젝트의 ESLint 설정에 따라 달라진다.

### 6-3. Prettier

Prettier는 들여쓰기, 줄바꿈, 따옴표 등 코드의 형식을 일관되게 정리하는 포맷터다. 여러 사람이 함께 작업할 때 코드 스타일 차이를 줄이고, 코드의 구조를 읽기 쉽게 유지하는 데 도움이 된다.

ESLint가 주로 코드의 문제와 규칙을 검사한다면, Prettier는 코드의 형식을 통일하는 역할을 한다. 두 도구의 연동 방식과 실행 명령은 프로젝트 설정에 따라 달라진다.

### 6-4. React Router

Todo List에서 미완료 Todo, 전체 Todo, 완료된 Todo를 각각 다른 페이지로 분리하기 위해 `react-router-dom`을 사용했다.

```bash
npm install react-router-dom
```

라우팅을 설정할 때는 `BrowserRouter`, `Routes`, `Route` 등을 사용할 수 있다.

```jsx
import { BrowserRouter, Route, Routes } from 'react-router-dom';

<BrowserRouter>
  <Routes>
    <Route path="/" element={<TodoPage />} />
    <Route path="/all" element={<AllPage />} />
    <Route path="/completed" element={<CompletedPage />} />
  </Routes>
</BrowserRouter>;
```

각 페이지의 역할은 다음과 같이 나누었다.

| 경로         | 페이지          | 역할                    |
| ------------ | --------------- | ----------------------- |
| `/`          | `TodoPage`      | 완료되지 않은 Todo 표시 |
| `/all`       | `AllPage`       | 전체 Todo 표시          |
| `/completed` | `CompletedPage` | 완료된 Todo 표시        |

Todo 상태와 추가·수정·삭제·완료 처리 함수는 공통 상위 컴포넌트에서 관리하고, 필요한 데이터를 각 페이지에 props로 전달하는 구조를 사용했다. 이를 통해 상태 관리와 페이지별 UI를 분리할 수 있었다.

### 6-5. 폴더 구조

페이지 컴포넌트와 공통 UI 컴포넌트를 분리해 관리했다. 프로젝트의 실제 폴더 구성에 따라 세부 파일은 달라질 수 있지만, 주요 역할은 다음과 같이 구분할 수 있다.

```text
src/
├── components/
│   ├── Button/
│   ├── Checkbox/
│   ├── Input/
│   ├── TodoItem/
│   └── Modal/
├── pages/
│   ├── TodoPage.jsx
│   ├── AllPage.jsx
│   └── CompletedPage.jsx
├── App.jsx
└── main.jsx
```

| 폴더/파일              | 역할                                   |
| ---------------------- | -------------------------------------- |
| `components/`          | 여러 페이지에서 재사용하는 UI 컴포넌트 |
| `components/TodoItem/` | 하나의 Todo 항목 표시 및 관련 동작     |
| `components/Modal/`    | 삭제 확인 모달과 관련 Context 관리     |
| `pages/`               | URL에 따라 보여줄 페이지 컴포넌트      |
| `App.jsx`              | 페이지 라우팅 및 공통 상태와 기능 관리 |
| `main.jsx`             | React 애플리케이션의 시작점            |

컴포넌트와 페이지를 분리하면 각 파일의 책임이 명확해지고, 공통 UI를 재사용하거나 기능을 수정하기 쉬워진다.

## 7. 3주차 학습 정리

이번 주차에는 라우팅의 여러 방식과 브라우저 렌더링 과정을 학습하고, Todo List 프로젝트에 Context API 기반의 삭제 확인 모달을 구현했다. 또한 개발 도구와 폴더 구조의 역할을 정리하면서 기능 구현뿐 아니라 코드의 유지보수성과 컴포넌트 간 책임 분리도 중요하다는 점을 확인했다.

특히 Context API 실습을 통해 여러 컴포넌트에서 공통으로 사용하는 상태와 함수를 Provider로 전달할 수 있다는 점을 익혔다. 앞으로 기능이 늘어날 때도 각 컴포넌트의 역할을 분명하게 나누고, 필요한 상태를 적절한 위치에서 관리하는 방향으로 개발하고자 한다.
